# オンライン対戦 設計メモ

友だちと各自の端末から参加して遊ぶオンラインモードの設計。**サーバー必須・パス＆プレイとは別物**。
2026-11-13 に endo が「オンライン対戦の設計から始める」を選択したため作成。まだ設計フェーズであり、
ホスティング契約など費用が発生する手順は endo の明示承認があるまで実行しない。

作成日: 2026-11-13 / 対象: `index.html`（単一ファイル、約194KB、8人固定）

## 1. 目的

- 離れた場所にいる友だちと、各自のスマホ／PC から Fake Bloom を対戦できるようにする。
- ソロ（人間1人 + CPU）とパス＆プレイ（1台を回す対面）は現行のまま壊さない。オンラインは第3のモードとして追加する。
- 秘密情報（実役職・夜の行動）が他プレイヤーに見えないことを最優先の要件とする。

## 2. 現行コードの前提（2026-11-13 時点で確認）

- 試合全体は単一のグローバル `state` に入り、1つのブラウザの中で完結している。
- ロジックの中核は DOM から比較的分離している：配役 `setupGame()`、夜の解決 `resolveNightActions()`、
  CPU の夜行動 `cpuNightActions()`、CPU の投票 `cpuVotePick()`、集計 `tallyVotes()`、勝敗 `checkWin()`。
  テストハーネスが IIFE を外してヘッドレス実行できている ＝ Node へ移植可能な形をしている。
- フェーズ遷移: `night` → `morning` → `discussion` → `vote` → `night` … → `end`。
- 秘密情報の例：バカの実役職と表示役職・うっかり flag、インポスター同士の仲間情報、各自の夜の行動と私的な結果、
  インポスター側の盗み見情報（`state.fakeIntel`）。
- 演出（カットイン・吹き出し・ステージのモーション・効果音）は、すべて公開情報からクライアント側で再生できる作り。

## 3. 基本方針：サーバー権威型（server-authoritative）

- **サーバーが唯一の真実（全 state）を保持する。** クライアントに全 state を配る案は、開発者ツールで
  中身を覗けば全員の役職が分かってしまうため採用しない。
- サーバーは各プレイヤーに「そのプレイヤーが見てよい情報だけ」を抽出したビュー（player view）を送る。
- クライアントが送るのは入力だけ（夜の対象選択・投票・議論の発言）。解決と抽選はすべてサーバー側。
- カットイン・吹き出し・モーション等の演出は、サーバーが配る公開イベント列から現行の仕組みで再生する。

## 4. 構成

- **クライアント**：現行 `index.html` に「オンライン」モードを追加。描画と演出は既存資産を再利用し、
  状態の出所を「ローカル state」から「サーバーから届く player view + 公開イベント」に差し替える。
- **サーバー**：Node.js + WebSocket の小さな常駐プログラム。試合ロジックは現行コードから抽出した
  共有モジュールを使い、ブラウザ版と二重管理にしない（フェーズ0 の仕事）。
- **ホスティング候補**（2026-11-10 調査済み、設計フェーズでは決定しない）：
  - Oracle Cloud Always Free：¥0。ただし人気リージョンの容量不足、アイドル回収、登録の手間などの注意点あり。
  - 国内小型 VPS：月 ¥326〜698 程度（ConoHa / さくらのVPS の最小プラン）。安定性はこちらが上。
  - 任意で独自ドメイン：約 ¥1,500/年。
  - いずれも**契約は endo の明示承認後**。まずローカル／無料枠で試験できる形に作る。

## 5. 部屋と参加フロー

- ホストが部屋を作成すると、4〜6文字の部屋コードが発行される。参加者はコードを入力して入室（合言葉方式）。
- アカウント登録はなし。入室時にセッション用トークンを端末へ保存し、再接続の本人確認に使う。
- 人間は 2〜8 人。不足分はサーバー側で CPU が埋める（現行の CPU ロジックを流用）。満員でなくても開始できる。
- 設定（インポスター人数・ボマー有無・難易度・議論タイマー）はホストが決め、サーバー経由で全員に同期する。
  難易度は CPU の強さのみに効かせる。

## 6. フェーズ進行と同期

- **夜**：各自が自分の端末で対象を選ぶ。全員の入力が揃うか、タイムアウト（目安60秒。未入力は「行動しない」扱い）で
  サーバーが一括解決する。インポスターの襲撃代表など、現行の解決ルールをそのまま踏襲する。
- **朝の報告**：サーバーが公開イベント列（誰が倒れた／防がれた／蘇生した等）を全員へ同時配信し、
  各クライアントがカットインとモーションを再生する。
- **議論**：CPU の発言はサーバー側で生成して配信。人間同士の会話手段は未決（§9-1）。
  議論タイマー（なし/1/2/3分）はサーバーが管理する。
- **投票**：各自が投票。全員分が揃うかタイムアウトで集計し、途中経過は見せない。政治家の2票など現行ルール踏襲。

## 7. 切断・再接続・放置対策

- 回線が切れてもセッショントークンで同じ席に戻れる（再接続）。
- 切断中のプレイヤーは「未入力＝行動しない／投票しない」として試合を止めずに進行する。戻ってきたら現在の
  player view を再送して復帰させる。
- ホストが抜けても試合はサーバー側で継続する（ホスト権限はロビーでのみ意味を持つ）。
- 部屋は試合終了後しばらく保持し、残っている人で再戦できるようにする。

## 8. 秘匿の担保

- サーバー→クライアントの送信は player view のみに限定する。含めてよいもの：
  自分の役職、インポスター同士なら仲間の情報、自分宛の夜の結果、公開情報（生存/脱落、公開された役職、
  公開イベント、議論の発言、投票結果）。
- バカには表示役職だけを送る（現行の Feign 式秘匿をサーバー側でも維持）。実役職とうっかり flag は
  結果画面のタイミングまでサーバー内に留める。
- テスト観点：各プレイヤー宛の送信データを検査し、他人の実役職・他人の夜入力が含まれないことを
  自動テストで担保する（現行の「のぞき見防止」テストのオンライン版）。

## 9. 未決事項（endo の判断待ち）

1. **議論フェーズの人間同士の会話手段**：自由入力チャット／定型文のみ／チャットなし（外部通話前提）。
   推奨は定型文＋短い自由入力だが、自由入力は誤送信・ネタバレ事故の扱いを決める必要がある。
2. **参加者の想定**：友だち同士のプライベート部屋だけか、知らない人とのマッチングも要るか。
   初期はプライベート部屋のみを推奨。
3. **ホスティング**：無料枠（Oracle）で始めるか、安定した小型 VPS（月数百円）にするか。
   費用が発生する契約は endo の明示承認後。
4. **表示名**：現行どおりキャラ（ルナ等）を自動で割り当てるか、参加者が表示名を決めるか。

## 10. 段階計画

- **フェーズ0：ロジック抽出** — 試合ロジックを UI から切り離し、Node でもブラウザでも動く共有モジュールにする。
  現行テストをそのまま移植先で通す。ソロ／パス＆プレイの挙動は不変。
- **フェーズ1：サーバー最小実装** — 部屋の作成/参加、配役、夜→朝→議論→投票→勝敗の1試合が
  CPU 混じりで最後まで回る。演出は最小限。
- **フェーズ2：クライアント接続** — タイトル画面にオンライン入口、ロビー画面、再接続表示。
  カットイン/吹き出し等の演出を公開イベントから再生する。
- **フェーズ3：仕上げと試験運用** — 切断・タイムアウト・ホスト退出の整備、スマホ表示の確認、
  endo と友人でのテストプレイ。

各フェーズは作り直しクラスの作業量になるため、定期開発ではバックログに小分けして順に進める。

## 11. 初期スコープ外

- 観戦モード、ランク／レーティング、フレンド登録、アカウント制、公開マッチング、ボイスチャット。
